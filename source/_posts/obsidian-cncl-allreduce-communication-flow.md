CNCL 是面向 MLU 设备的集合通信库，提供类似 NCCL 的多卡、多机通信接口。本文以 `AllReduce` 为例，梳理集合通信库从初始化、拓扑建立到运行时算法选择的大致数据流。

> 本文只保留可迁移的公开架构和通信语义，省略具体实现环境细节。

## 1. 对外接口可以分成三类

集合通信库的 C API 通常包括：

1. 通信原语：`Broadcast`、`Reduce`、`AllReduce`、`AllGather`、`ReduceScatter` 以及点对点 `Send/Recv`。
2. 通信器管理：创建、销毁、查询 rank 和设备信息，以及配置通信器。
3. 组操作：用 `GroupStart/GroupEnd` 将多个通信操作批量提交，减少调度开销。

其中，通信器（Communicator）保存一次集合通信所需的 rank 数量、当前 rank、设备和连接资源，是运行时分发操作的核心对象。

## 2. 初始化阶段：先建立“谁和谁通信”

调用初始化接口后，库需要把进程身份、设备能力和拓扑关系组织起来：

```text
初始化通信器
    ↓
带外 Bootstrap：交换 rank 和设备信息
    ↓
构建设备可达性矩阵
    ↓
生成环、树、全连接或层次拓扑
    ↓
为拓扑边分配链路、队列和缓冲资源
    ↓
交换连接信息并建立数据通道
    ↓
把可用算法注册到通信器
```

这里的带外通信只负责“交换建立连接所需的信息”，真正的数据仍然通过设备链路、网络或共享内存传输。初始化完成后，一个通信器通常持有多种算法对象和对应的传输连接。

## 3. AllReduce 运行时如何被分发

用户调用 `AllReduce` 时，入口层通常依次完成以下工作：

1. 校验 buffer、数量、数据类型和归约操作是否有效。
2. 读取 rank 数量、数据规模、设备连接能力和当前通信器状态。
3. 根据这些条件选择合适的拓扑和算法。
4. 将操作分发给具体算法，并把任务提交到设备队列。

抽象后的调用链可以表示为：

```text
AllReduce API
    ↓
参数检查与上下文恢复
    ↓
算法选择器
    ↓
Ring / Tree / AllConnected / Hierarchical
    ↓
Processor 调度器
    ↓
设备链路、网络或共享内存传输
```

算法选择一般不是固定映射，而是启发式决策。例如，小数据且设备之间有高速互联时，全连接或单步算法可能更合适；数据量较大或跨节点通信时，环形或分层环形算法往往更容易获得稳定带宽。

## 4. 为什么要把算法、拓扑和传输分层

这类实现常把通信逻辑拆成三层：

- 拓扑层描述节点之间的连接关系，以及环、树、分层结构等逻辑路径。
- 算法层描述如何在拓扑上执行 AllReduce，例如分块、流水和归约顺序。
- 传输层负责具体的数据通道，如设备互联、网络和共享内存。

分层后，同一种 Ring 算法可以复用不同传输后端；当硬件拓扑变化时，也可以只替换拓扑或传输实现。通信器则负责把已经初始化好的对象组合起来，并在运行时完成选择和调度。

## 5. 阅读这类代码时的主线

面对一个集合通信库，不必一开始就追所有文件。可以沿着四个问题阅读：

1. API 入口如何检查参数并定位通信器？
2. 通信器何时完成 rank、拓扑和连接资源初始化？
3. 算法选择依据哪些运行时条件？
4. 选中的算法如何把逻辑步骤转换成设备队列操作？

抓住这条主线后，再去看 Ring、Tree 或特定设备传输的细节，会比从某个 kernel 或连接类反向摸索更容易建立整体认识。
