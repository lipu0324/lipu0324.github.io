让 Agent 在远程机器上执行一条命令并不困难。真正麻烦的是命令前后的工作：选对环境、同步代码、准备依赖、启动多节点任务、持续读取日志，以及在失败以后保留现场、回收资源。

如果每接入一种测试都重新写一套远程脚本，测试流程很快就会和环境管理纠缠在一起。一次失败可能来自代码，也可能来自旧镜像、错误的工作目录或没有启动的某个节点。最后只看见一个退出码，很难知道究竟发生了什么。

这篇文章把相关实践整理成一个通用思路：让远程执行服务管理环境生命周期，让测试 Skill 定义测试步骤和验收条件，再由 Agent 根据实际执行结果推进任务。文中的接口名称和配置均为说明设计用的示例，不依赖某个内部工具或特定部署平台。

## 先把职责分清楚

MCP 可以把环境探测、命令执行、日志读取等操作提供给 Agent，但这些工具本身不一定理解测试的领域含义。测试 Skill 则是一份可复用的流程说明，告诉 Agent 何时运行什么检查、如何解释结果，以及遇到失败以后应该怎么办。

| 角色 | 需要负责的内容 |
| --- | --- |
| 项目配置 | 允许使用的主机、镜像、凭据引用、代码位置和环境变量 |
| 远程执行服务 | 准备环境、同步文件、启动与取消命令、读取日志、收集产物、回收资源 |
| 测试 Skill | 前置条件、测试命令、覆盖范围、判定规则和证据清单 |
| Agent | 根据当前状态执行流程，解释结果，并在需要决策时向用户说明依据 |

最容易混淆的地方是“命令成功”和“测试通过”。远程服务返回退出码 `0`，通常只说明它启动的进程正常退出。假如测试根本没有发现用例、漏跑了一个节点，或者 benchmark 输出缺少错误计数，就还不能判定本次测试通过。

因此，执行服务可以报告 `SUCCEEDED`，但测试是否为 `PASS`，需要继续按照测试 Skill 的规则检查。

## 配置描述期望，环境清单描述实际结果

配置文件适合保存相对稳定的信息，例如代码应该同步到哪里、允许使用哪些机器、需要什么镜像。密码和私钥应通过凭据引用传入，环境配置文件也不应该被意外提交进公开仓库。

但真正执行时，配置并不总等于事实。容器可能被重新创建，调度平台可能分配了不同的工作节点，远端运行目录也可能为本次任务单独生成。

环境准备结束以后，服务应返回一份实际环境清单。例如：

```json
{
  "environment_id": "env-example",
  "state": "READY",
  "launcher": "node0",
  "nodes": ["node0", "node1"],
  "workspace_id": "workspace-example",
  "lease_expires_at": "<expiry-time>"
}
```

这只是示意结构。实际清单还可以包含镜像摘要、实际工作目录、资源身份和运行权限等信息。它应该成为后续执行的依据，而不是让 Agent 根据主机名称或者上一次运行的记录猜测环境。

对于多机测试，确认能够登录也只是第一步。SSH 走通，并不能说明测试需要的数据网络、网卡接口或设备互联已经可用。控制通道和数据通道需要分别检查。

## 把准备过程当作一个有状态的任务

创建容器、同步大目录或等待调度资源，都可能花费较长时间。如果工具调用超时以后只能重新执行整套准备，就很容易产生重复容器和遗留任务。

更合适的接口是先返回任务标识，再查询状态。一次准备过程可以包含这些状态：

```text
CREATED → PREPARING → READY → IN_USE → CLEANED
                 ↘ FAILED
```

重复查询应该观察同一次任务，而不是启动新的准备。重试同一个尚未结束的请求时，可以使用稳定的请求标识实现幂等性；如果任务已经失败，修正原因后再建立新的一次尝试。

服务还需要保存资源的身份和归属。这样，即使 Agent 会话或执行服务中断，后续也有机会重新连接到活动任务，或者精确回收已经创建的资源。

不过，持久化一个状态文件不等于后台任务一定能够继续运行。准备和执行是否依赖当前服务进程、断开后是否能够恢复，都需要由工具的实际契约说明。Agent 应遵守这个契约，不能把“有状态记录”理解成“随时可以关闭服务”。

## 用结构化执行保留上下文

当环境进入 `READY` 后，测试可以开始。但一个可追溯的执行请求需要比一段命令字符串多一些信息。

例如，下面是一种通用的请求表示方式：

```json
{
  "environment_id": "env-example",
  "commands": [
    {
      "node": "node0",
      "argv": ["python", "-m", "pytest", "tests/smoke", "--junitxml=results/smoke.xml"]
    }
  ],
  "timeout_seconds": 600
}
```

节点、参数和超时都明确列出来，后面就能核对本次到底执行了什么。需要 shell 的管道或重定向时，也应该显式说明使用的 shell 和脚本来源。结构化参数有助于减少转义错误，但它本身不能替代权限和范围控制。

多节点任务还需要说明由谁启动进程。如果分布式启动器已经负责向所有节点分发任务，就应从指定的 launcher 启动一次；如果使用独立分片，则分别向各节点提交自己的分片。两种方式混用，可能让同一组测试被重复启动。

代码同步也应该留下依据。源代码版本、工作区差异、实际构建的产物，以及最终运行的程序需要能够对应。否则，即使测试结果正确，也无法确定它验证的是不是刚刚修改的版本。

## 日志不是最后几行

运行中的日志尾部适合观察进度，但不能总是用来支撑最终结论。某个节点可能在前面已经报告了错误，后面的进程却继续输出；汇总脚本也可能因为忽略一个退出码而显示正常结束。

远程执行服务最好分别保存各节点的标准输出、标准错误和退出码，并支持按偏移读取完整日志。对于大型任务，还应提供独立的报告与产物收集接口，避免把所有文件内容塞进一次工具响应。

Agent 在结束前至少应该能回答：哪些节点实际参与了，哪些命令已经结束，哪些日志读完整了，必要的报告是否存在，以及测试失败究竟发生在哪个阶段。

对于目录或二进制文件，同步与收集结果可以附带文件数、大小和校验值。这些信息能帮助确认传输是否完整；至于文件里记录的结果是否正确，还需要进一步按领域规则检查。

## 把 PASS 写成可以核对的条件

测试 Skill 最重要的部分，是把“应该成功”展开成具体判据。

| 测试类型 | 退出码之外需要核对的内容 |
| --- | --- |
| 单元测试 | 用例数量是否符合预期，失败数和错误数是否为零，跳过项是否合理 |
| 编译测试 | 目标产物是否生成，版本、架构和构建配置是否正确 |
| 分布式训练 | 所有 rank 是否结束，关键数值是否有效，检查点和报告是否齐全 |
| 通信测试 | 数据规模与参与者是否覆盖完整，正确性检查是否开启，结果行是否缺失 |
| 性能测试 | 预热、重复次数和统计口径是否一致，时延或带宽是否满足约定目标 |
| 负向测试 | 预期故障是否真的发生，错误类型和发生阶段是否符合设计 |

例如，一项“断开节点后的恢复测试”不能只检查程序最后退出了。还需要确认节点确实断开、系统走过了预期恢复路径、其他参与者没有永久挂起，最终状态也符合要求。

测试结论还应区分三个情况：`PASS` 表示约定的判据全部满足；`FAIL` 表示执行或检查发现了不满足条件的结果；`BLOCKED` 表示环境、设备或依赖不足，尚未真正完成验证。把缺少环境写成测试通过，会让后续判断失去依据。

## 失败之后，先保存证据再清理

测试环境常常是共享的。按进程名结束所有任务，或者仅凭容器名称执行删除，都可能影响不属于本次运行的资源。

资源管理最好建立在创建时记录的身份上：某个执行任务拥有哪个进程组，某个环境创建了哪些容器和临时目录，哪些资源只是借用的。取消和清理接口据此限定范围，并且允许安全重试。

自建短期容器和调度平台提供的容器也应该区别处理。前者可以由创建它的服务回收，后者通常由平台管理；一次测试只能清理自己在其中创建的运行产物。

失败后的合理顺序是：确认活动任务状态，读取日志，收集需要保留的产物，再取消剩余执行并清理本次资源。需要继续调试时，可以为环境续租，并向使用者说明保留到什么时间。

## 测试 Skill 应该留下哪些内容

一个实用的测试 Skill 可以围绕六个问题组织：

1. 它适用于什么工程和测试类型？
2. 用户需要提供哪些目标与环境信息？
3. 开始测试前必须确认哪些条件？
4. 如何启动任务、观察状态和处理失败？
5. 什么证据满足 PASS，什么情况属于 FAIL 或 BLOCKED？
6. 哪些产物需要保留，结束后如何释放资源？

不必把所有逻辑都堆进一段临时生成的“万能脚本”。真正稳定、需要复用的测试工具可以作为项目源码维护；Skill 则应说明每个阶段的作用、输入和判据，让 Agent 能观察中间结果并作出下一步判断。

这样，当某个检查失败时，我们能知道是环境准备、代码构建、测试执行，还是结果判定出了问题。新增测试也可以复用同一套环境管理能力，只补充它真正关心的领域规则。

远程测试自动化最终要交回的，是一份可以继续检查的结果：本次运行的环境、代码和配置，实际执行的命令，各节点结果，以及已经通过和仍未覆盖的验证范围。有了这些信息，Agent 才能把远程执行变成一个可以托付、也可以追溯的工作过程。
